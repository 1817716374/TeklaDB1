# 7.64 DB2 与工程编号系列关联

`parseNumberingDatabase` 新增原生7.64布局，读取系列名称、前缀、起始号和保存的零件/装配计数，保留其余字段与原始容器。`readProject` 继续默认不配对没有工程GUID的旧DB1/DB2；调用者明确启用 `trustLegacyNumberingBasenames` 后，同目录、同基本文件名、同存储版本的7.64库可以建立对象→编号系列关联。

## 原生证据

来源为[U52公开教学工程](https://btscm.fr/dicocm/R/realisations/u52_2007vierge.zip)，与[7.64 DB1/IFC证据](DB1_764.zh-CN.md)属于同一工程。新增四个固定成员：主DB2、空组件DB2、7.30历史DB2备份和 `numbering.history`；所有源归档和文件的大小、SHA-256固定在 `tests/corpus.json`，不随仓库分发。

主DB2解压后464字节：12字节 `Xsteel\x80 7.64` 文件头、九个顺序表，表22有四条76字节系列记录。四个记录标签均为4。组件DB2只有12字节文件头，无表、无系列，属于合法空库。7.64文件头不带数据库GUID；后续二进制表ID即使低字节是空格、句点或数字，也不应被吞进版本字段或当作GUID分隔符。

与同包7.30备份比较，四条系列的所有保存值相同、顺序不同。测试按系列键比较，不用行序推断生命周期或最新状态。

| 系列 | 保存的零件计数 | 保存的装配计数 |
|---|---:|---:|
| A/1 | 0 | 20 |
| P/1 | 0 | 3 |
| F/1 | 3 | 0 |
| /1 | 41 | 0 |

这八个值与日志最后记录的对应 `Max Part` / `Max Assembly` 一致。计数不是当前对象数量，也不能单独给对象赋号。其余四个整数槽保留在 `additionalFields`；不把非零槽猜成钢筋计数、删除状态或标志。

## 对象与范围

编号日志中的65个零件、38个装配，与当前DB1对象引用恢复出的类型、系列及保存编号逐项一致。两条历史身份3957和3961未在当前引用中找到；它们被记录为未匹配，不解释为已经删除，也不自动套用GUID迁移。

启用明确的旧库文件配对后，主DB1产生105条系列关联，`pairingEvidence` 为 `ExplicitLegacyBasename`。其中4527和5069只有系列关联，序号为0、`positionNumber` 为空；系列存在不等于已分配编号。主DB1仍保留75条编号记录和545条引用，包括零引用与未配对系列。

组件DB1的五条编号记录保留，组件DB2为空，因此组件系列关联为0。它不会借用主DB2中的同名前缀。错误存储版本、缺少配对文件，以及默认未确认范围的情况，都不产生对象系列关联。关闭原始伴随文件读取不影响显式开启的编号解析和配对。

## 复现与限制

```sh
python -B tools/test_numbering764_evidence.py --data /path/to/external-corpus --download --exe /path/to/tekladb1_validate --work /path/to/external-tests
```

Python按表头行数、宽度和表尾独立遍历原生DB2，再逐项比较C++字段；C++另读取Tekla编号日志核对计数及对象编号。21项原生/工程检查包含普通与GZIP输入、空库、修改计数、修改日志、未知字段保留、重复键、错误尺寸/标签/头部、截断、错误版本配对、缺少DB2及原样恢复对照。

新增六组合成边界测试和三项安装后消费测试；追加九项固定语料回归，原789文件、1,669项期望保持不变；现793文件、1,678项全部通过。完整表边界处截断与合法少表文件无法仅从这类无全局表数的容器区分；未知表仍保留原始记录。DB2比较快照、当前有效编号、其他整数槽语义、跨工程身份关系和编号生命周期没有因此完成。

C++17/C++20默认回归各526项、MSVC/OCCT 534项全部通过。新增7.64 DB2证据测试在MinGW C++17/C++20和MSVC三种编译结果均通过；安装核心35项、OCCT 42项通过。测试产物均留在外部工作目录。
