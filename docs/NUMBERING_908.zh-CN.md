# 9.08 DB2 与 DB1 对象编号

9.08 的 DB2 系列、保存计数和 DB1 对象关联已恢复，工程入口报告 `PartialSemantic`。比较快照、删除/重新编号后的有效状态及其他表含义仍未恢复。

## 样本和独立核验

使用[官方考试工程](https://github.com/TrimbleSolutionsCorporation/TSOpenAPI_Model_Exam)的7月及后续9月快照，来源及固定提交同[DB1 9.08](DB1_908.zh-CN.md)。新增固定两份主DB2、两份组件DB2和7月包内的 `numberinghistory.txt`，共5份文件；压缩包/成员、大小、SHA-256见 `tests/corpus.json`。它们仍是同一工程，不作为两个独立设计项目。

编号日志日期为2021年7月6日，包含4,677个零件和259个装配。按GUID匹配7月DB1，每个对象的类型、系列、前缀及位置号均与日志相同。9月DB1仍匹配4,677个零件和257个装配，两条历史GUID已不在模型身份表中：

- `68a5241b-0cba-40b4-a7f8-2dc6b1975189`
- `3bd0c7f1-0c2a-4854-b1e9-41ebeba14f37`

不据此猜测对象的删除原因或生命周期，也不要求后来的模型保有全部历史对象。

| 系列键 | DB2 零件计数 | DB2 装配计数 | 日志最大编号 |
|---|---:|---:|---:|
| `M/1` | 262 | 0 | 零件262 |
| `/1001` | 68 | 0 | 零件1068 |
| `B/1` | 0 | 667 | 装配667 |

三组独立历史最大值均满足 `start + counter - 1`，包括非1起始号1001。保存计数不是对象数量；例如259个日志装配的最大编号是667。该证据也不证明任意工程在删除、重编号之后都遵循相同的当前有效状态规则。

## 字段与关联

主库为49字节版本/GUID头及10张顺序表；表22的三条记录各80字节。另9张表在样本中为空，仍完整保留。xslib.db2只有49字节头，属于有效的空库。

系列记录与已验证的现代DB2一致：载荷0..51为系列键，52..55为零件计数，56..59为装配计数，60..79保留为未命名整数。按最后一个 `/` 分割前缀与起始号；不要求起始号为1。版本、GUID、行长度、表尾和键的合法性均检查，未知表保留原始记录并诊断。

DB1表211的对象ID/编号记录引用分别位于载荷0/8；零件表322、装配表323的起始号/序列位于8/12，前缀分别位于20/28。解析保留原始记录，仅在已有有效范围规则内派生位置号。第三类钢筋编号仍不派生分配号。

工程入口按同路径基名、存储版本、数据库GUID配对，再精确匹配前缀与起始号。7月有6,158条对象→DB2系列关联，9月有6,163条；关联数量不是已编号对象数量。所有日志核验的现存对象均有对应系列关联。没有匹配系列、特殊起始值或歧义的对象不制造关联；错GUID/版本仍可读取两个文件，但不配对对象。组件库的空DB2不会被主库系列代替。

## 复验

```sh
python -B tools/test_numbering908_evidence.py --data /path/to/corpus --download --exe /path/to/tekladb1_validate --work /path/to/separate-work
```

七种变异验证检查有效：DB2计数、非1起始号、DB1序列、指向另一有效编号记录的引用、独立日志标记、数据库GUID及版本。后两种同时确认模型仍能加载、对象关联为空。九项合成测试覆盖有效主库、空组件库、尺寸/键/表尾错误、重复系列、截断、缺GUID和未知表原始保留。安装后测试亦覆盖非1起始系列与空库。Windows下载及测试目录放在E盘。

新增14项完整语料回归：两份快照各含原始主/组件DB2、系列语义、主/组件DB1编号记录和独立日志/工程关联。原语料期望不变。此处的GUID/日志字段一致性有独立来源支持；其余原始字节、指纹和关联数量属于回归/一致性检查，不能作为完整生命周期或几何真值。
