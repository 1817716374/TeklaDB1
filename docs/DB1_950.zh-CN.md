# DB1 9.50 身份字段证据与边界

## 样本

四份 Tekla Structures 2023 SP8 DB1 主库及其 BIM4LCA IFC4 配对文件已按归档成员、字节数与 SHA-256 固定在 `tests/corpus.json`。样本只由 `tools/corpus.py --download` 下载到语料目录，不随源码仓库分发。IFC 导出只用来验证身份与装配关系，不作为 DB1 几何真值。

## 已验证的布局与关系

DB1 9.50 ordinal 353 有 32-byte payload 和六个字段描述符 `(1,1,1,1,1,0)`。每行前 16 字节是四个 little-endian u32，之后是 16-byte GUID。现有解析器将第一个 u32 暴露为对象 ID，并将 GUID 字节解码为 `Identity::guid`；四个原始字也通过 `rawIdentityWords` 原样提供。第 4 个 u32（索引 3）暴露为 owner ID。其余三个整数没有语义命名。

独立校验器 `tools/test_db1_950_evidence.py` 不调用 C++ 语义解析结果：它从 DB1 table 353、part table 274、assembly table 300 与配对 IFC4 STEP 行重新读取证据，并检查压缩 IFC GUID 的 128-bit 解码、对象分类和 `IFCRELAGGREGATES` 父子 owner 关系。可从仓库根目录运行：

```powershell
$corpus='E:\CodexData\TeklaDB1-review\corpus' # 改成自己的外置语料目录
$build='E:\CodexData\TeklaDB1-review\build17' # 改成自己的外置构建目录
$env:TEMP='E:\CodexData\TeklaDB1-review\tmp'
$env:TMP=$env:TEMP
cmake -S . -B $build
cmake --build $build --target tekladb1_validate
python -B tools/corpus.py --manifest tests/corpus.json --data $corpus --download --exe "$build\tekladb1_validate.exe"
python -B tools/test_db1_950_evidence.py --corpus $corpus
```

四个样本结果：

|---|---:|---:|---:|---:|---:|---:|
| Housing Concrete | 65,943 | 36,045 | 17,397 | 16,827 | 570 | 719/719 |
| Housing Timber | 25,088 | 4,454 | 2,137 | 1,649 | 488 | 1,652/1,652 |

匹配到的非装配 GlobalId 对应 table 274 中的 part ID；`IFCELEMENTASSEMBLY` GlobalId 对应 table 300 中的 assembly ID。owner 交叉校验只计父子双方都能在 IFC 与 DB1 身份表中解析的聚合边。

四份 DB1 身份表中的 owner 字段有一个悬空值：`Housing_Timber_BuildingPermit` 对象 26445923 保存 owner ID 26446239，但该 ID 不在此 DB1 的身份表中。其余非零 owner 均能在同一身份表中找到。解析器保留该原始 owner 值并逐条增加 `unresolved owner ID` 诊断，不强制把整个模型判为损坏，也不会为这条关系构造对象链接。5,017 条 IFC 聚合边核验只覆盖父子 GUID 均成功匹配的边，不涵盖这条悬空身份引用。

另对 GUID 成功配对的 IFC 产品按身份表第二个原始整数分组。四个样本分别有 3、3、3、2 个整数值对应多个 IFC 实体类；例如 Housing Concrete 的 2049467 同时出现在 IFCWALL、IFCSLAB、IFCBEAM、IFCCOLUMN、IFCFOOTING 和 IFCBUILDINGELEMENTPART。这个整数不能作为 IFC 实体类型直接解码，当前也没有独立依据把它命名为 Tekla 对象类别，因此继续保留为 `rawIdentityWords`。

## 其余整数的值域审计

对四个完整身份表逐行统计四个 u32，并与身份 ID、part ID、assembly ID 集合对照。原始字 1（索引 1）每个工程只有 19–27 个不同值，且没有一个值等于本 DB1 身份 ID；配对 IFC 又已证明这些值不能直接解释为 IFC 实体类。原始字 2（索引 2）则大多等于本行对象 ID，但例外随样本变化很大：Housing Concrete 为 65,525 行自等、329 行指向另一身份 ID、89 行为零；Housing Timber 为 17,755 行自等、7,328 行指向另一身份 ID、5 行为零；Office Concrete 为 125,304 行自等、42 行指向另一身份 ID、206 行为零；Office Timber 为 97,480 行自等、42 行为零。非零值通常也落在 DB1 身份 ID 集合中，但这种数值/键重合本身不能说明它是别名、引用或其他字段。

另外检查了相邻旧版中作为 identity-class 表的 ordinal 315：四份 9.50 样本该表均为 28-byte 行布局但记录数为零。因此这些样本没有可直接连接的类别表记录，不能把身份行里的整数按旧版 class-reference 逻辑解释。该检查只排除了这条特定映射途径，不证明 ordinal 315 在所有 9.50 数据库中都为空，也不确定其余字段的用途。

原始字 2 的“通常自等”以及跨工程差异显著的例外尚未通过独立 Tekla 导出或另一个可解释表得到验证。因此四个 u32 仍全部按原值保留；没有把索引 2 改名为重复对象 ID/引用，也没有由它生成额外关系。`tools/test_db1_950_evidence.py` 现会固定并逐次核对上述值域分布，属于字段假设筛查，不构成新的字段语义声明。

进一步拆分非自等行后，四个样本的 word2 目标均能在身份表中找到，但没有一个目标 ID 出现在 part table 274 或 assembly table 300，也没有一个目标 GUID 出现在配对 IFC 的 GlobalId 集合中。目标身份的 word1 与来源身份 word1 在这些行中均不相等。不同工程的结构也不一致：Housing Concrete 有 329 条来源指向 8 个目标身份，目标 word1 只有一个取值且 8 个目标的 word2 都自等；Housing Timber 有 7,328 条来源指向 174 个目标，目标 word1 有两个取值，其中目标自身的 word2 有 81 个自等和 93 个非自等；Office Concrete 有 42 条来源指向 4 个目标，目标 word1 只有一个取值；Office Timber 没有非自等行。独立校验器会固定这些计数，并核对目标不属于 part/assembly 表、目标 GUID 未出现在配对 IFC 中、来源和目标 word1 不相等。

这说明 word2 的例外包含跨身份目标，且不是 part/assembly 主键的直接引用；它尚不能说明这些身份代表什么，也不能证明该字段在所有对象上都遵循同一语义。尤其 Timber 样本中目标身份本身还出现多种 word2 形态，因此目前不把它命名为别名、父级、原型或组件引用，也不将它接入公共对象关系图。

## 尚未恢复

- 除对象 ID 与 owner ID 外，身份行中其余三个 u32 的字段角色；现有证据不足以确认它们对应 identity class/type、context、别名或其他关系。
- part 的具体 `PartType`。解析器保留 part 记录，但将其类型留为未知。
- 依赖 identity class 的钢筋分类、引用校验以及相关语义关系。
- 9.50 的所有表字段、几何与各类引用；本次只新增了已由此四份样本交叉验证的身份/owner 片段。

因此版本状态是 **PartialSemantic**，不等同完整 9.50 支持。IFC GlobalId 匹配和聚合 owner 一致性是跨文件身份证据，不证明 IFC 与 Tekla 保存了相同几何、全量对象或当前生命周期状态。完整语料回归另外运行 C++ `model_950` 四项；独立脚本负责校验其关键外部字段依据。


## Tekla 2023 SP4 工程交叉核验

额外固定的 Abri-Moto-VCCF25 工程提供了独立 9.50 主 DB1 与 IFC 配对样本。DB1 记录 1,715 个身份、177 条 part、106 条 assembly、109 条 bolt-group 和155条 weld 记录。该工程的155个表190行ID都唯一命中身份；表192中的310条 type-13 链接各自把一个 weld 连到两个不同的表274 part；其放置、坐标基与定义引用均在对应表中闭合。IFC 中55个 `IFCFASTENER` 的 GlobalId 均唯一命中这些 weld 行，且导出名称均为 `Weld`。据此，解析器仅对9.50的表192/type-13关联源且同时存在表190 weld行的身份标记 type 13，再使用现有已验证的 weld/placement/frame/part 链读取路径。四个 BIM4LCA 9.50 IFC样本没有这些 weld 行，因此本次不会从它们推断其它关联类型或扩大映射。

这些 155 条 weld 不是身份表中所有对象类别的完整分类证据；不从 IFC 导出反推其它身份类型。part 类型仍未恢复，177 条 part 继续留在 `unhandledPartIds`，`actualPartIds` 为空。不要把“已连接映射 part 行”误读为“已恢复零件类型”。

独立校验器 `tools/test_db1_950_evidence.py` 读取 IFC GUID 和 DB1 原始身份/对象表，确认 158 个 IFCBEAM/IFCCOLUMN/IFCPLATE/IFCMEMBER 身份均命中 part 表，99 个 IFCELEMENTASSEMBLY 均命中 assembly 表，108 个 IFCMECHANICALFASTENER 均命中 table 310，另有55个 `IFCFASTENER('Weld')` 唯一命中 table 190 weld 行。310 条 type-13 链接覆盖155个 weld 且各有两个不同 part 目标。266 条两端均有身份的 IFC 聚合边中，158 条与 DB1 identity owner 字段相符；其余边不作 owner 对应声明。该样本扩展不恢复剩余 identity word、其它9.50对象类型或图纸字段语义。
